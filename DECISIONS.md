# Decisions

Where SPEC.md was unclear, the simplest option was chosen and is recorded here.

## Phase 1

1. **Scaffold written by hand, not `create-next-app`.** The folder already contained SPEC.md, and the generator refuses or prompts in a non-empty folder. The result is the same layout (App Router, `src/`, Tailwind, `@/*` alias).
2. **Tailwind CSS v4** (CSS-first config in `globals.css`, no `tailwind.config.js`). It is what current shadcn/ui targets.
3. **shadcn/ui components are added by copying** (`src/components/ui/button.tsx`, `card.tsx`) plus `components.json`, so `npx shadcn add <name>` works later. Only the components Phase 1 needs exist.
4. **Prisma 6** (not 7), pinned to avoid the config-file and driver-adapter changes in v7. TypeScript 5.9, Node 22 in Docker (spec asks for Node 20 or newer).
5. **Column naming:** Prisma fields are camelCase; database tables and columns are snake_case via `@map`/`@@map`, matching the spec's field names.
6. **IDs are `cuid` strings.** `Token.code` is a separate 8-character public code (alphabet without 0/O/1/I/L), generated with `crypto.randomInt`.
7. **`Token.date` is a Postgres `DATE`** holding the hospital-local calendar date (Asia/Kolkata). The unique key is `(department_id, date, seq_no)` as specified. The "row lock" for the next `seq_no` will lock the Department row (`SELECT ... FOR UPDATE`) in Phase 3, so no counter table is needed.
8. **Added `User.must_change_password`** (not in section 4) to implement "forced password change on first login" from section 9. Seeded users have it set to true.
9. **`OpdSession.start_time` / `end_time` are `"HH:MM"` strings** in the hospital's local time, not timestamps.
10. **`QueueEvent.action` and `AuditLog.action` are free strings**, not enums, so new actions do not need migrations. Allowed values are enforced in code.
11. **Single-stage Dockerfile that keeps dev dependencies.** This makes `docker compose exec app npx prisma db seed` work as the spec's install steps say, at the cost of a larger image. Migrations are applied on container start (`prisma migrate deploy`).
12. **Initial migration is generated with `prisma migrate diff`** from the schema, because no database was available while scaffolding.
13. **`POSTGRES_PASSWORD` added to `.env.example`** so the database password is set in one place. `DATABASE_URL` must use the same password.
14. **`/api/health` and `/health` are public on purpose.** They return only up/down and row counts, no personal data. Docker uses the API route as its healthcheck. This is the only API route without a role check in Phase 1; all later routes follow the spec's "Who" column.
15. **Backup service and Caddy are not in `docker-compose.yml` yet.** Spec section 5 assigns backups to Phase 5.
16. **Seed is re-runnable.** Users, departments, rooms and doctors use upserts; the 50 demo tokens are only created if no tokens exist for today. Demo patients use fake names and phone numbers.
17. **Seed doctors are linked to the department's single room**, and each department gets one doctor, as the spec's seed list says (4 doctors).

## Phase 2

18. **Auth.js v5 (`next-auth@beta`)** with the Credentials provider and JWT sessions. v5 is still tagged beta but is the version built for the Next.js App Router. Session lifetime is 12 hours (one clinic shift).
19. **The JWT cookie is not trusted for authorisation.** Middleware uses it only to decide where to redirect the browser. Every API route calls `requireRole()` and every page calls `requirePageRole()`, and both re-read the user from the database. A deactivated user or a changed role therefore takes effect on the next request, not when the cookie expires.
20. **API routes are not covered by middleware** (excluded in the matcher). Each route checks its own role, as the master prompt requires. `tests/unit/api-roles.test.ts` loops over every admin route and every role to make sure none is missed.
21. **Forced password change is enforced in three places:** middleware redirects pages to `/change-password`, `requireRole()` returns 403 `PASSWORD_CHANGE_REQUIRED` for everything except `POST /api/me/password`, and pages redirect. After a successful change the user is signed out and logs in again, which avoids a stale session flag.
22. **Admin-set passwords are temporary.** Creating a user, or setting a password in the user edit form, sets `must_change_password`. Passwords must be 8 to 72 characters (bcrypt ignores bytes after 72). bcrypt cost is 12 as the spec says.
23. **Login does not reveal which phone numbers exist.** An unknown phone is compared against a dummy hash so the response time is the same. Login rate limiting is a Phase 5 item (spec: rate limits on public routes), so it is not in yet.
24. **Phone numbers are stored as 10 digits** starting 6 to 9. `+91`, `91` and `0` prefixes and spaces are accepted on input and removed.
25. **Role access to page areas:** `/admin` ADMIN only; `/desk` CLERK and ADMIN (spec: ADMIN may create tokens); `/doctor` DOCTOR only. After login each role lands on its own area.
26. **Admin API follows the spec table (GET, POST, PATCH)** with these additions and limits: `DELETE` exists only for OPD sessions (a wrong session otherwise could not be removed); departments and users are switched off with `active` instead of being deleted; a department's `token_prefix`, a room's department, and a doctor's login and department cannot change after creation (existing tokens and doctors depend on them).
27. **Safety rules on users:** an admin cannot change their own role or deactivate themselves (prevents locking everyone out); a user with a doctor profile cannot be given another role; creating a doctor profile sets the user's department to match.
28. **Generic admin screen.** The five setup screens share one client component (`AdminCrud`) driven by a field list, to keep the code small. Screens call the same `/api/admin/*` routes that are tested.
29. **Not in Phase 2:** the language toggle on the login page and Hindi text (next-intl is added in Phase 6, per the build phases); the check-in QR poster (needs `/checkin` from Phase 4); the CSP header (Phase 5 security work); `GET /api/departments` (Phase 3 with the queue APIs).
30. **`trustHost: true`** in Auth.js, because the app is reached by a LAN IP or hostname that is not known in advance. Session cookies are marked `Secure` automatically when the site is served over HTTPS (Caddy, Phase 5); on plain `http://` LAN access they cannot be.
31. **Audit log:** logins, password changes and every admin create, update and delete are written to `audit_logs` with the actor and IP. No names or phone numbers are stored in the log text.

## Phase 3

32. **Skip is implemented with a new column, `tokens.skip_hold`.** The spec says a skipped token "re-enters after the next 3 waiting tokens" and lists SKIPPED to WAITING as automatic. So a skipped token stays SKIPPED while `skip_hold` counts down by one for every patient the same doctor calls, then becomes WAITING again with its own priority and token number. The hold is 3, or fewer if fewer patients are waiting; when nobody else is waiting it returns at once. If the doctor presses Next and only skipped patients remain, they all return first. The engine can predict the call order (`predictCallOrder`), so "people ahead" is exact.
33. **A later emergency still goes first.** Because a returned patient competes by priority and token number, an emergency who arrives while a patient is skipped is called before them, and counts as one of the 3 calls.
34. **Whose queue is it.** A doctor's queue is the waiting tokens assigned to them plus tokens assigned to nobody ("any doctor"). Calling a token assigns it to the calling doctor. A doctor sees only their own queue; desk staff and admins see the whole department.
35. **Next, as pressed by a doctor:** refused with 409 while a called patient has not been started, skipped or marked no-show; automatically completes a patient who is still in consultation (so one press moves the line along); 409 "nobody is waiting" otherwise, with no change made.
36. **Who may do what (API table in the spec says DOCTOR, CLERK):** skip, recall, no-show, start, complete and transfer are open to doctors, clerks and admins (admin added because the spec lets admins create tokens). Cancel is clerk and admin only. Doctors are limited to their own department, and for skip, recall, no-show, start and complete to patients they called. `next` is doctors only.
37. **Recall** does not change the status. It adds one to `recall_count` and writes a `recall` event, which the TV board (Phase 4) will use to announce the token again.
38. **Cancel** is allowed for waiting, called, in-consult and skipped tokens. The spec says "any to CANCELLED"; done, no-show and cancelled tokens are final, so cancelling them is refused.
39. **Transfer** moves a waiting token to another doctor of the same department, or back to "any doctor". Moving to another department would need a new token number, so it is not allowed.
40. **Token numbers.** `seq_no` is the highest number of that department on the hospital's local date plus one, taken while the department row is locked (`SELECT … FOR UPDATE`), so parallel requests never clash (20 parallel creations gave 20 consecutive numbers). The local date uses `hospitals.timezone` (Asia/Kolkata), so numbering restarts at local midnight. The printed form is `MED-034` (3 digits, more if needed).
41. **Estimated wait** = average consult time of the doctor's last 20 finished patients × people ahead. If no history exists it uses 10 minutes. Consults of 0 minutes or over 3 hours are ignored (usually a forgotten Complete press). For a token assigned to nobody the department's last 20 are used.
42. **Consent at the desk.** The new-token form has a required tick box ("I have told the patient…") and each token creates a `ConsentRecord` (purpose "OPD queue", notice version `v1`, channel DESK). The proper notice text and versioning come in Phase 5.
43. **Patient search** needs the full 10-digit phone and returns at most 5 matches, so the patient list cannot be browsed. Staff screens show patient names and ages, never phone numbers. The phone number is not written to the audit log.
44. **Status API is built now.** `GET /api/tokens/:code/status` is public and returns no personal data. Its folder is named `[id]` (it holds the code) because Next.js allows only one dynamic name per level next to `/api/tokens/[id]/[action]`. Rate limits for public routes arrive in Phase 5. The patient page `/t/<code>` arrives in Phase 4, so the QR on the slip leads nowhere until then.
45. **NOTIFY** is sent inside each queue transaction on channel `queue_<departmentId>` with a small payload (type, action, token id, token label). There is no personal data in it. The listener and SSE are Phase 4; until then the desk and doctor screens re-read their data every 5 to 8 seconds.
46. **Slip and QR.** The QR is made in the browser with the free `qrcode` package and points to `APP_URL/t/<code>`. The slip prints through the browser print dialog with `@page { size: 58mm auto }`. It shows hospital, token number, department, doctor, room, time and the QR, and no patient name.
47. **Not enforced:** `max_tokens` and session hours on OPD sessions. The spec stores them but says nothing about refusing tokens, so desks can still issue tokens early or late.
48. **The audit trail of a skip** has two entries, `queue.skip` and later `queue.requeue`, so both the skip and the moment the patient came back are recorded. Every queue action also writes a `queue_events` row in the same transaction.

## Phase 4

49. **SSE is fed by one Postgres `LISTEN` connection per server process** (the free `pg` package; Prisma cannot listen). `src/lib/sse.ts` fans each `queue_<departmentId>` notification out to the open streams. If the connection drops it reconnects with growing delays (1 s up to 30 s), listens again, and sends every stream a `resync` event, because notifications sent in the gap are lost. Tested with a fake `pg` client, and live by restarting the database while a stream was open.
50. **One stream can follow several departments:** `/api/stream/<id>,<id>...` (at most 12). Browsers allow only about 6 open connections per site, and a desk screen shows every department. The stream is open to a valid display key (`?key=`) or any logged-in user, as the spec says. Events carry only the token label and ids, never names. A heartbeat comment goes out every 20 seconds, and the response uses `no-transform` so nothing buffers it.
51. **Screens reload their state, they do not apply events.** On every event, on every (re)connect, and every 20 to 30 seconds as a safety net, a screen fetches its state again. The browser side uses its own backoff (1 s, 2 s, 4 s ... up to 30 s) instead of the browser's built-in retry. A lost event therefore cannot leave a screen wrong for long. Measured: a doctor's Next reached an open stream in about 0.4 s.
52. **TV board.** `/display/<ids>?key=` is a client screen that reads `/api/display/<ids>?key=`. That state contains only token numbers, room names, department names and the next 3 tokens, one card per doctor (titled with the room, or the doctor's display name when there is no room). It cannot contain patient data because the query never selects it; `display-service.test.ts` checks this. A missing or short (under 8 characters) `DISPLAY_KEY` never opens the board. The key is in the URL, so the page sends no referrer.
53. **Announcements come from changes in the state, not from events.** A call is announced when a room's (token, recall count, called time) is new, so a recall is announced again, a missed event does not mean silence, and nothing is announced twice. Calls already on screen when the page opens are not announced. Each is a chime (made with the browser's audio, no sound files), then English, then Hindi: "Token M E D 34, room number 4." and "टोकन एम ई डी 34, कमरा नंबर 4।". The room number is taken from the end of the room name; if there is none the name is spoken. Only the token number and room are ever spoken.
54. **Sound needs one press of OK on the TV.** Browsers refuse sound until someone interacts with the page. The board shows a large button for it. Voices come from the TV browser's text-to-speech; if it has no Hindi voice, the Hindi line may be read in another voice or not at all. **This needs a test on the real TV or stick.** The board also asks the browser to keep the screen awake.
55. **Token status page `/t/<code>` re-reads every 5 seconds** (and when the tab becomes visible) instead of using the stream, because the stream needs a login or the display key. It shows place, people ahead and estimated wait, and "It is your turn" with a phone vibration when called; it shows no names. The code is accepted in lower case too. Page text is English with the department also in Hindi; full Hindi comes in Phase 6.
56. **Self check-in `/checkin`.** Three typed fields (name, phone, age) and two taps (department, sex), plus the consent tick box. The spec says "3 fields"; the patient record also needs department and sex, so they are tap buttons rather than typing. Priority is decided by the server: 60 and over go in the elderly group, everyone else is normal. Pregnant, disabled and emergency patients are registered at the desk. A self check-in is not assigned to a doctor.
57. **Check-in is safe to press twice.** If the same name (any capitals) and phone already has an unfinished token in that department today, that token is returned instead of a new one. The patient record is reused for the same phone and name. Family members sharing one phone use different names and get their own tokens.
58. **Limits on `POST /api/checkin`, as in the spec:** 5 per phone per day (counted from today's self check-in tokens) and 30 per IP per hour (counted from `checkin` audit rows). See item 70 for how reliable the IP is. Limits for the other public routes were added in Phase 5.
59. **Consent at check-in** is stored as channel SELF, notice version `v1`. The notice is shown in English and Hindi on the page, with the real `RETENTION_DAYS`. The text is written into the page for now and moves to the translation files in Phase 6.
60. **Poster and TV links.** Admin, "Poster & TV" shows the TV address of each department (and of all together) with the key filled in, and an A4 poster with the check-in QR code for printing. The page tells the admin when `APP_URL` or `DISPLAY_KEY` is missing.
61. **Desk and doctor screens now use the stream** and refresh when something changes, instead of every 5 to 8 seconds (the old polling hook is removed). They still re-read every 30 seconds as a fallback.
62. **After a database restart** the stream recovers by itself, but Prisma can fail the first request that used an old connection (error P1017); the next request works. For a hospital server this happens only when Postgres restarts.

## Phase 5

63. **Reports** (`GET /api/reports/daily?from&to`, ADMIN; screen Admin, Reports). For each day and department: tokens, done, no-show, cancelled, still open, self check-in, average wait and average consult time. *Wait* is the time from getting a token to being called the first time, for patients who were called. *Consult* is Start to Complete for finished consultations; consults of 0 minutes or over 3 hours are ignored (a forgotten Complete press), the same rule as the wait estimate. Without dates it shows the last 7 days. The report covers at most 92 days at a time because it is added up in memory; averages are rounded to one decimal.
64. **CSV export** (`GET /api/export/tokens.csv?from&to`, ADMIN) has one row per token and **no patient names, phone numbers or ages**, only token number, department, doctor, visit type, priority, status, source, times in hospital time, wait and consult minutes, and recall and skip counts. It is streamed 500 rows at a time and may cover up to 366 days. It starts with a byte order mark so Excel reads Hindi correctly, and text starting with `=`, `+`, `-` or `@` gets an apostrophe in front so a spreadsheet cannot run it as a formula. Each export is written to the audit log.
65. **Charts are plain SVG and HTML**, no chart library and no client JavaScript. The department colours from the seed failed the colour check for charts (the teal is too dull to tell from grey, and magenta and blue are too close for colour-blind readers), so charts use the validated categorical palette in a fixed order by department name: blue, orange, aqua, yellow, and so on. A 9th department would be grey. Every chart has a legend and prefix labels, and the same numbers are in a table below it.
66. **Consent notice** now lives in one place (`src/lib/consent.ts`) with a version (`v1`). The desk shows it for the clerk to read out, the check-in page shows it, and every token stores a `ConsentRecord` with purpose, version, channel (desk or self) and time. When the wording changes, change the text and raise the version number; old records keep the version the patient saw. Admin, Privacy shows the current notice and the number of records.
67. **Retention job.** `node-cron` runs inside the app (started from `instrumentation.ts`) every night at 02:30 hospital time, and once 2 minutes after the app starts so a server that was off at night catches up. It replaces the name with "Anonymised patient" and empties phone and ABHA number for patients whose **last visit** (newest token, or the day they were added if they never had one) is older than `RETENTION_DAYS` (default 90; a missing or invalid value means 90). Age, sex and all token records stay, so counts and reports are unchanged. It can be run again safely. Each run writes `retention.run` to the audit log with the number anonymised (in the item column, never personal data). `DISABLE_JOBS=1` turns it off. If you run more than one copy of the app, move this job to its own container.
68. **A patient's own data request** (Admin, Privacy): find one patient by full phone number, download everything held about them as JSON (details, visits, consents), or erase them. Erasing is the same as retention: name, phone and ABHA number are removed and the visit rows stay, because deleting them would change past counts. Consent records stay as proof of what was agreed; they hold no personal data. The phone number searched for is not written to the audit log.
69. **Backups** run in a separate `backup` container (Postgres 16 tools, gpg, cron) every night at 02:00 in `BACKUP_TZ`. `pg_dump` output goes straight into AES-256 encryption with `BACKUP_PASSPHRASE`, so no readable copy is written to disk. Before a backup is kept it is decrypted and read back (`pg_restore --list`). Files are `./backups/queuecare-<date>.dump.gpg`; those older than `BACKUP_KEEP_DAYS` (14) are deleted. The script refuses the example passphrase, and `docker compose` will not start without a `BACKUP_PASSPHRASE`. **Lose the passphrase and a backup cannot be opened.** The folder is on the same machine as the database, so copy it elsewhere (a USB drive or another computer) as well. `scripts/restore.sh` restores into a NEW database, refuses an existing name, and removes the new database again if the restore fails. Tested: backup, wrong passphrase, and a full restore with matching row counts.
70. **Rate limits** (in addition to check-in's 5 per phone per day and 30 per IP per hour): login 10 tries per phone and 30 per IP in 15 minutes (cleared by a successful login; the login page says to wait 15 minutes); token status 60 per code and 120 per IP per minute; the status page 60 per IP per minute; check-in bursts 10 per IP per minute; wrong display keys 20 per IP per minute; password changes 10 per user in 15 minutes. Answers are 429 with a `Retry-After` header. Counters are kept in the app's memory, so a restart resets them. When the IP is not known, visitors share one bucket that is 10 times larger. **How reliable the IP is:** the app uses the first `x-forwarded-for` value if one is sent, otherwise the connection address. Behind Caddy that is the real visitor address. Without Caddy a visitor can send a fake header and avoid the per-IP limits (the per-phone, per-code and per-user limits still hold). On Docker Desktop for Windows or Mac all devices appear as one gateway address, so per-IP limits are shared between them; a Linux server does not have this problem. Because logins are limited per phone number, someone can lock a clerk out for 15 minutes by guessing; the admin can wait or ask them to try later.
71. **Audit log screen** (Admin, Audit log): newest first, 50 per page, filter by date range and by the start of the action name (`queue.`, `login`, `patient.` and so on). It shows hospital time, who, action, item and IP. It never holds patient names or phone numbers.
72. **Caddy for HTTPS is optional** (`docker compose --profile https up -d`, address in `SITE_ADDRESS`). The Caddyfile uses Caddy's own certificate authority (`tls internal`) for a LAN address, with a note on how to use a public domain. Only the compose file was checked; **it was not run** in testing. Port 3000 stays open, so close it in the server's firewall if you use Caddy.
73. **`.gitattributes`** keeps the shell scripts and the Caddyfile on LF line endings, so they still work when the project is cloned on Windows.

## Phase 6

74. **Language is a cookie, not part of the web address.** `next-intl` runs without language prefixes (no `/hi/...`), so every link, QR code and TV address stays the same. The choice is saved in the `NEXT_LOCALE` cookie for a year by the English / हिन्दी switch (on the login page, the staff header, the check-in page, the token status page and the landing page). With no cookie, the browser's language is used, then English. The simplest option that keeps printed posters valid.
75. **Every screen has its text in `messages/en.json` and `messages/hi.json`.** `npm test` fails if the two files differ in keys or placeholders, if any text is empty, or if the Hindi file is mostly English. `npm run i18n:check` finds keys used in the code that are missing from either file. To add a language: add its code to `src/i18n/config.ts`, copy `en.json` to `<code>.json`, translate it.
76. **API error text.** The server still answers in English with a stable `code`. On screen, English shows the server's wording (it can be more specific); Hindi shows our translation of the code (`errors.<CODE>`), and falls back to the server's text for a code with no translation. A test checks that every code the API can send has a translation.
77. **Two things are always bilingual, not by cookie:** the TV board (a TV has nobody to press a switch, and it already speaks both languages) and the printed check-in poster (it hangs on a wall for everyone). The consent notice is shown in both languages at the desk (the clerk reads it out) and in the visitor's language on the check-in page. Department names follow the language (`nameEn` / `nameHi`). Audit log action codes stay as stored (technical).
78. **Landing page at `/`** (`src/app/(marketing)/page.tsx`) follows section 11 of the spec. It is server-rendered with no client JavaScript except the language switch. The two statistics link to the real articles (Medical Dialogues, 14 Feb 2023; ThePrint, 10 Jun 2025); the 50 to 4 minutes figure is marked as an official claim, as the spec asks. A web search showed other sources date the Bihar baseline differently (August 2023 against August 2024); the page follows ThePrint's own wording as the spec does. Lighthouse on mobile: accessibility 100, best practices 100, SEO 100 (the tool did not report performance).
79. **Addresses that depend on who hosts the page come from `.env`, never guessed:** `GITHUB_URL` (footer link, install box, ADMIN_GUIDE link), `DEMO_URL` (the "Try the live demo" button) and `CONTACT_EMAIL` (default `contact@example.org`, the spec's placeholder). With no `DEMO_URL` the demo button opens this server's login page; with no `GITHUB_URL` the install box shows `<repository-address>`. The Hindi and English landing text is only sent to the server, not to the browser.
80. **Page titles and descriptions are put in `<head>` for every visitor** (`htmlLimitedBots: /.*/` in `next.config.ts`). Next.js 15 otherwise streams them into `<body>`, which Lighthouse and some search crawlers do not read.
81. **PWA with Serwist.** `src/sw.ts` keeps only the app's own scripts, styles and fonts (cache-first, fingerprinted files) and the icons, plus a static two-language `/offline` page that is shown when a page cannot be fetched. It **never stores pages, queue data or API answers**: patient screens must be live, and a shared hospital phone must not keep a patient's page. The worker is built only in production (`next build`), and is off in `npm run dev`. The manifest starts at `/login`; icons are drawn on request by `/icons/<name>.png` (no image files in the repository).
82. **Installing the app needs `localhost` or HTTPS.** Browsers only offer "install" and run service workers on `https://` or `localhost`. Over plain `http://192.168.x.x` the site works as before but is not installable. Use the optional Caddy profile (DECISIONS 72) to get HTTPS on the hospital network.
83. **Lock file.** `@swc/helpers` is listed as a dependency because Serwist needs it and `npm ci` inside the Linux image failed without it in the lock file.

## Phase 7

84. **End-to-end tests (Playwright, `tests/e2e`) drive a running app** in Chromium, with one worker because every test shares one queue. They create their own test department (prefix `TST`), room, clerk and doctor straight in the database with a known password, and switch them off afterwards, so they never touch the demo users or passwords. They do leave a few finished tokens behind, so they must never run on a hospital's real database (said in the README). Locally the database must be reachable from the computer: `docker-compose.e2e.yml` opens it on `127.0.0.1` only, for tests, never on the hospital server.
85. **What the end-to-end tests check:** the spec's flow (a clerk creates a token, the doctor presses Next, the TV board shows the call within **2 seconds**, the patient's page says "It is your turn!", then the visit completes), that the TV never contains the patient's name, patient self check-in by QR, who may open what (anonymous, clerk, wrong TV key; page redirects and API 401/403), the English / Hindi switch, and the landing page and installable-app files.
86. **Bug found and fixed by the first end-to-end run:** after a successful login without a requested page, the address bar still showed `/login` while the desk was on screen. The login now lands on `/post-login`, a tiny page that sends each person to their own home page (or to the password change).
87. **GitHub Actions** (`.github/workflows/ci.yml`) on every push to `main` and every pull request: *checks* (lint, types, translation keys, unit tests), then in parallel *e2e* (fresh Postgres 16 service, migrate, seed, build, start, Playwright) and *docker* (compose file is valid, the app and backup images build). The report and app log are kept for 7 days when the end-to-end job fails. This workflow could not be run from here, only written; its first real run is on GitHub.
88. **A real hospital starts without the seed**, so there was no way to create the first admin. `scripts/create-admin.ts <phone> "<name>"` creates the hospital record and an admin with a random temporary password (printed once, must be changed at first login). It refuses a bad number or a number already used. Tested against a scratch database.
89. **Seed demo data now also has history.** Besides today's 50 tokens, the seed adds the six days before today (no Sundays) of finished and no-show visits with plausible waits (6 to 35 minutes) and consult times, so Reports shows a chart on a fresh install. It only adds history when there is none, so the seed stays safe to run again.
90. **ADMIN_GUIDE.md restore steps were run for real**: backup, restore into `queuecare_restored`, stop the app and backup, rename the databases (`queuecare` to `queuecare_old`, `queuecare_restored` to `queuecare`), start: the live database came back with the same counts. Renaming (rather than editing `DATABASE_URL`) keeps the nightly backup, which is tied to the name `queuecare`, pointing at the live data.
